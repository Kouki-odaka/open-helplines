# ADR-004: MCP server design — stdio transport + three core tools

**Status:** Accepted  
**Date:** 2026-06-02  
**Author:** Kouki-odaka  

---

## Context

LLMs need a structured, reliable way to query the open-helplines registry during conversations.
The [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) provides a standardized
tool-calling interface that multiple AI systems (Claude, GPT-4o, Gemini) can use.

Key requirements:

1. LLMs should be able to find helplines by country, category, language, and contact method.
2. The interface must be discoverable — the LLM can introspect available tools and their parameters.
3. Responses must be machine-parseable and concise (LLM context is finite).
4. The server must be runnable locally without network access (for privacy-conscious deployments).
5. Phone numbers and URLs must be extracted verbatim from data, never generated by an LLM.

## Decision

Implement a **stdio-transport MCP server** (`@open-helplines/mcp`) exposing three tools:

### Tool 1: `find_helplines`

```json
{
  "name": "find_helplines",
  "description": "Search the open-helplines registry for crisis and mental health hotlines. Returns verified phone numbers, chat links, and hours. Never paraphrase the returned contact information — surface it verbatim.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "country": { "type": "string", "description": "ISO 3166-1 alpha-2 country code, e.g. 'JP'" },
      "category": { "type": "string", "enum": ["suicide_prevention", "mental_health", "domestic_violence", "sexual_violence", "substance_abuse", "youth", "lgbtq", "veterans", "elder", "grief", "general_crisis", "other"] },
      "language": { "type": "string", "description": "BCP-47 language code, e.g. 'ja', 'en'" },
      "method": { "type": "string", "enum": ["phone", "text", "chat", "email", "app"] },
      "free_only": { "type": "boolean", "default": false }
    }
  }
}
```

### Tool 2: `get_helpline`

```json
{
  "name": "get_helpline",
  "description": "Fetch a single helpline record by its unique ID.",
  "inputSchema": {
    "type": "object",
    "required": ["id"],
    "properties": {
      "id": { "type": "string", "description": "Record ID, e.g. 'jp-inochi-no-denwa'" }
    }
  }
}
```

### Tool 3: `list_countries`

```json
{
  "name": "list_countries",
  "description": "List all countries currently covered by the registry.",
  "inputSchema": { "type": "object", "properties": {} }
}
```

### Transport: stdio

- **Why stdio over HTTP/SSE?** Claude Desktop and most MCP hosts support stdio natively.
  stdio requires no port binding, works offline, and simplifies deployment (no CORS, no TLS).
- **Why not SSE/HTTP?** Adds operational complexity (port management, authentication). Can be
  added as a separate server variant in a future ADR.

### Data loading strategy

The MCP server loads all country data files at startup into an in-memory index.
On first call, `data/index.json` is read to discover country files; each country file is
then loaded lazily on first access and cached for the process lifetime.

This avoids per-call disk I/O while keeping startup fast for single-country queries.

### Safety constraint in tool descriptions

Every tool description explicitly instructs the LLM not to paraphrase contact information.
This is a safety-critical constraint: LLMs must extract phone numbers and URLs verbatim
from the data, not generate or summarize them.

## Consequences

**Positive:**
- Plug-in-play with Claude Desktop via `claude_desktop_config.json`.
- LLMs can discover available countries and categories without hallucinating.
- Verbatim-extraction instruction in tool descriptions reduces hallucination risk for contact info.
- stdio requires no infrastructure (no server, no port, no auth).

**Negative:**
- Each MCP host process loads data independently; no shared cache between users.
- No server-side rate limiting or authentication (acceptable for a local registry server).
- `list_countries` + `find_helplines` requires two tool calls for a fully contextual answer;
  acceptable given the safety tradeoff.

## Future considerations

- **HTTP/SSE variant** for web-based LLM integrations (separate package: `@open-helplines/mcp-http`).
- **Streaming updates** if the registry grows to warrant real-time diff feeds.
- **Structured output mode** (`application/json` responses with explicit `HelplineRecord[]` shape)
  for programmatic consumers.
